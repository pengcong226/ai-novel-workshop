## 二、优化方向分析

### 方向 A：Pipeline 智能化升级（10-Agent 进一步完善）

#### A1：体裁感知的审计权重动态调整

**现状问题**：ContinuityAuditor 的17维审计对所有体裁使用相同的权重。但实际上：
- 玄幻/仙侠：力量体系一致性、升级节奏是核心，权重应最高
- 言情：角色情感弧线、CP互动质量是核心
- 悬疑：线索铺设、逻辑自洽是核心
- 都市：现实逻辑约束是核心

**已有基础**：`types/genreProfile.ts` 已定义 `GenreAuditDimension`，`ContinuityAuditor.ts:207` 已读取 GenreProfile，但**未用于权重调整**。

**方案**：
1. 在 GenreProfile 的 `auditDimensions` 中增加 `weight` 字段（1-10）
2. ContinuityAuditor 在计算 `overallScore` 时，按体裁权重加权
3. 审计报告标注"体裁敏感维度"标签

**工作量**：1 人日

---

#### A2：伏笔治理引擎（Hook Governance + Arbiter）

**现状问题**：当前伏笔健康系统（hookHealthAnalyzer.ts）能诊断压力和陈旧，但缺少**准入控制和冲突解决**：
- 无限制新增伏笔 → 活跃伏笔膨胀（>15个时读者难以追踪）
- 两个伏笔依赖同一事件但矛盾 → 无冲突检测
- 伏笔回报期望模糊 → 无法判断是否值得种植

**InkOS 参考**：
- `hook-governance.ts`（199行）：准入决策（需声明 type + expectedPayoff）
- `hook-arbiter.ts`（332行）：冲突检测（依赖图 + 家族冲突）

**方案**：
1. 新增 `hookGovernance.ts`：`admitHook()` 准入决策 + 活跃上限控制
2. 新增 `hookArbiter.ts`：`detectConflicts()` 依赖图冲突检测
3. 集成到 HookPromoter（Phase 9），新伏笔需通过准入检查

**工作量**：2 人日

---

#### A3：State Validator（状态校验器）

**现状问题**：StateSettler 在 Phase 7 写入实体和状态事件后，无二次校验。如果 LLM 提取的状态与已有状态矛盾（如角色A在本章死亡但下章又出现），不会被发现。

**InkOS 参考**：`state-validator.ts`（322行），用 LLM 比对新旧 truth files，检测矛盾。

**方案**：
1. 新增 `stateValidator.ts`：比对新写入的 StateEvent 与已有 Entity 状态
2. Phase 7 完成后，对关键实体（本章出场的角色）执行状态一致性校验
3. 矛盾标记为 critical 级 issue，写入审计报告

**工作量**：1.5 人日

---

### 方向 B：用户体验提升

#### B1：写作统计仪表盘

**现状问题**：WritingDashboard 显示当前字数、完成进度、Pipeline 状态，但缺少**写作行为数据**：
- 每日写作字数趋势（激励用户持续创作）
- 章节质量评分历史曲线（直观看到提升/退步）
- Token 消耗与成本追踪（帮助用户控制开支）
- 创作时段热力图（了解自己的高效时段）

**已有基础**：`TokenUsagePanel.vue` 有 Token 追踪，`tokenUsage.ts` 有用量计算，但分散且无时间维度聚合。

**方案**：
1. 新增 `useWritingStats` composable：聚合每日字数、评分、Token、时段数据
2. 在 WritingDashboard 新增"写作统计"区域，含3个图表：
   - 日写字数折线图（近30天）
   - 章节评分趋势线
   - Token 消耗分布饼图
3. 数据持久化到 IndexedDB（`writing-stats` store）

**工作量**：2 人日

---

#### B2：章节版本对比视图

**现状问题**：`chapterVersioning.ts` 支持快照创建和回滚，`ChapterVersionPanel.vue` 支持快照列表浏览，但**无法直观对比两个版本的差异**。用户只能分别打开两个版本凭记忆比对。

**方案**：
1. 新增 `VersionDiffViewer.vue`：双栏对比视图，差异高亮
2. 使用 `diff` 算法（或 `jsdiff` 库）计算文本差异
3. 支持选择任意两个版本进行对比
4. 集成到 ChapterVersionPanel 中

**工作量**：1.5 人日

---

#### B3：TypeScript 编译错误清零

**现状问题**：24 个 TS 编译错误，集中在：
- WritingDashboard.vue（6个）：Store 类型到 `Record<string, unknown>` 的不安全转换
- ProjectList.vue（4个）：ProjectConfig 类型不兼容

这些错误虽不阻塞构建，但影响代码可维护性，且可能导致运行时异常。

**方案**：
1. 修复 WritingDashboard 中的 Store 类型转换（使用 `as unknown as Record`）
2. 修复 ProjectList 中的 AdvancedSettings 类型兼容
3. 将 `vue-tsc --noEmit` 加入构建检查

**工作量**：0.5 人日

---

### 方向 C：现有功能深度优化

#### C1：大纲质量增强与自动扩展优化

**现状问题**：当前大纲系统（outlineGenerator.ts + outlineTemplates.ts）提供了经典结构模板和结构化编辑，但：
- 大纲章节缺少质量评分（如"本章冲突强度"、"钩子密度"）
- 自动扩展（PipelineRunner Phase 0 中的大纲耗尽自动扩展）使用简单的尾部追加，缺乏全局节奏规划
- 无大纲版本管理，扩展后无法回退

**与张力曲线的协同**：A1 的张力曲线分析结果应反哺大纲规划，实现"先规划节奏，再填充内容"。

**方案**：
1. 为大纲每个章节节点增加 `estimatedTension` 字段（0-100）
2. 大纲自动扩展时，调用 `tensionCurvePlanner` 计算已有节奏，插入合适张力的章节
3. 大纲扩展前创建快照（复用 chapterVersioning 机制）

**工作量**：1.5 人日

---

#### C2：上下文构建深度优化 — 记忆检索增强

**现状问题**：当前 ComposerAgent 的上下文组装依赖确定性的 smartTrim + mustKeep 关键词匹配。对于长篇小说（50+ 章），关键词匹配无法捕捉语义关联，导致：
- 相关但未提及关键词的早期章节被裁剪
- 角色隐含关系（如"A的师父B"中提及A时未检索B）被遗漏

**已有基础**：`vector-service.ts` 支持 OpenAI Embeddings + 本地 @xenova/transformers，`vector store` 已可用。

**方案**：
1. 在 ComposerAgent 中增加可选的向量检索路径
2. 使用章节摘要的 embedding 做语义相似度检索（top-K）
3. 与确定性 smartTrim 结果合并去重
4. 仅在用户启用向量服务时使用（默认关闭，避免首次构建索引延迟）

**工作量**：2 人日

---

#### C3：AI模型调用策略优化

**现状问题**：当前 FailoverManager + ModelRouter 已实现模型故障转移和成本感知路由，但缺少：
- **渐进式降级**：Token 预算不足时，自动从大模型切换到小模型完成剩余章节
- **章节复杂度预判**：所有章节使用相同模型，简单过渡章节也用高成本模型造成浪费
- **批量续写模型策略**：批量续写时前3章用高质量模型建立基调，后续章节自动切换到经济模型

**方案**：
1. 在 BatchContinueScheduler 中增加渐进式降级逻辑
2. 新增 `chapterComplexityEstimator.ts`：基于大纲意图和大纲节点估算复杂度
3. 批量续写时，前3章（或用户配置）使用高质量模型，后续自动降级

**工作量**：1.5 人日

---

### 方向 D：差异化功能

#### D1：多结局分支叙事

**现状问题**：当前系统是线性叙事，一章接一章。但网文用户越来越期待互动性，而"分支叙事"是AI写作的独特优势——人工写多分支成本极高，AI则天然适合。

**方案**：
1. 新增 `BranchNarrativeManager.ts`：管理叙事分支树
2. 在章节级别支持"分支点"标记，同一分支点可生成多条路径
3. WritingDashboard 中可视化分支树（类似Git分支图）
4. 每条分支独立维护状态和伏笔
5. 支持分支合并（两条路径重新汇聚到同一主线）

**差异化价值**：这是人工写作几乎无法实现的能力，是AI写作工具的核心差异化。

**工作量**：3 人日

---

#### D2：角色对话模拟器

**现状问题**：当前 ObserverAgent 可提取角色语言风格，但用户无法与角色"对话"来探索角色深度或测试对话一致性。

**方案**：
1. 新增 `CharacterSimulator.ts`：基于角色 Entity + 语言风格档案，模拟角色对话
2. 在 Sandbox 中增加"角色对话"入口，用户可选择角色进行对话
3. 对话上下文包含角色描述、关系、最近状态
4. 对话可用于测试角色一致性、激发灵感、验证对话风格

**差异化价值**：将 AI 写作工具从"生成器"升级为"创作伙伴"，用户可与自己的角色互动。

**工作量**：2 人日

---

#### D3：写作风格迁移

**现状问题**：StyleAnalyzerAgent 可分析5维风格指纹，但仅用于审计。用户无法将某位作家的风格应用到自己的小说上。

**方案**：
1. 新增 `styleTransferEngine.ts`：基于风格指纹，生成"风格迁移"修订指令
2. 用户可从"风格库"中选择目标风格（如"古龙风"、"金庸风"、"江南风"），也可上传参考文本自动提取风格
3. 修订时保持剧情不变，仅调整表达方式
4. 与 ReviserAgent 集成，作为新的修订模式 `style-transfer`

**差异化价值**：风格迁移是AI写作的高级应用，直接满足"写得像XX"的明确需求。

**工作量**：2 人日

## 四、建议实施策略

### 阶段一：质量闭环（4 人日）

**C3 → A2 → A3 → A1**

先清零 TS 错误（0.5d），再补齐 Pipeline 质量闭环：伏笔治理（2d）+ 状态校验（1.5d）+ 体裁感知权重（1d，可与 A2 并行）。

**目标**：Pipeline 从"能写出"升级为"写得好且有保障"。

---

### 阶段二：体验深化（3.5 人日）

**B1 → B2 → C1**

写作统计仪表盘（2d）让用户"看得见进步"；版本对比（1.5d）让修订"一目了然"；大纲增强（1.5d）与张力曲线协同实现"节奏驱动创作"。

**目标**：用户从"能用"升级为"爱用"。

---

### 阶段三：智能增强（5.5 人日）

**C2 → C3（模型策略） → D2**

记忆检索增强（2d）解决长篇核心痛点；模型调用策略优化（1.5d）降本增效；角色对话模拟器（2d）是差异化的第一步。

**目标**：系统从"工具"升级为"创作伙伴"。

---

### 阶段四：差异化突破（7 人日）

**D3 → D1**

写作风格迁移（2d）满足高频需求；多结局分支叙事（3d）是AI写作的终极差异化能力，但复杂度最高，需谨慎评估。

**目标**：建立竞品无法复制的核心壁垒。

## 五、风险提示

| 风险 | 影响 | 缓解 |
|------|------|------|
| D1 分支叙事状态隔离复杂度高 | 可能需 2 倍预估时间 | 先做最小可用版（仅2分支），验证后再扩展 |
| C2 向量检索首次构建索引慢 | 50+章项目可能需 1-2 分钟 | 异步后台构建，先展示 toast 提示 |
| B1 统计数据持久化增量 | 累积数据量需管理 | 保留90天明细，更早数据仅保留日汇总 |
| A2 伏笔治理准入可能过于严格 | 用户意图种植的伏笔被拒绝 | 提供"强制准入"选项，记录但不阻断 |

## 六、与竞品（InkOS）的差异化定位

| 能力 | InkOS（CLI） | 工坊（Web/Desktop） |
|------|-------------|-------------------|
| 交互方式 | 命令行 | 可视化仪表盘+沙盘 |
| 世界观管理 | Markdown文件 | 可视化实体/关系图/时间线 |
| 读者模拟 | 无 | 3群体差异化评估 |
| 张力曲线 | 单章节奏 | 跨全书张力曲线+仪表盘可视化 |
| 分支叙事 | 无 | 规划支持（D1） |
| 角色互动 | 无 | 规划支持（D2） |
| 风格迁移 | 无 | 规划支持（D3） |
| 体裁智能 | 通用审计 | 体裁感知权重（A1） |

**核心差异化方向**：InkOS是"程序员的AI写作引擎"，工坊应成为"创作者的AI写作伙伴"——可视化、互动式、可感知。
