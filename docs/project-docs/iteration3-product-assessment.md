## 二、仍有提升空间的领域

### 2.1 上下文智能裁剪（尚未实现）

**现状**：ComposerAgent 使用固定字符预算截断（`SECTION_LIMITS` + `clampText`），不根据当前章节意图做相关性排序。

**InkOS 方案**：`governed-context.ts` + `governed-working-set.ts` 根据 ChapterIntent 的 mustKeep 决定保留优先级，按相关性评分裁剪低价值内容。

**增强建议**：
1. 在 ComposerAgent 中引入意图感知的上下文排序——mustKeep 指定的元素优先保留
2. 伏笔池按 `advancePressure`（伏笔压力）排序，高压力伏笔优先纳入上下文
3. 角色矩阵按本章出场角色过滤，不出场的次要角色信息裁剪
4. 章节摘要按距当前章的远近加权，越近权重越高

**预估工作量**：2 人日

### 2.2 章节节奏分析（尚未实现）

**InkOS 实现**：`chapter-cadence.ts` 分析最近 N 章的场景类型分布、情绪张力曲线、标题聚集检测。

**工坊现状**：无等价功能。ContinuityAuditor 有"节奏检查"维度，但仅依赖 LLM 判断，无确定性的节奏模式检测。

**增强建议**：
1. 在 ChapterAnalyzer 中增加确定性的节奏分析
2. 从章节摘要中提取章节类型（战斗/日常/过渡/高潮/喘息）
3. 检测连续同类型章节（≥3 章）→ 警告节奏单调
4. 检测连续高张力章节（≥4 章）→ 警告读者疲劳
5. 检测标题词汇重复 → 警告标题同质化

**预估工作量**：1.5 人日

### 2.3 审计维度深度增强

**现状**：ContinuityAuditor 有 16 个审计维度，其中部分维度的 `checkInstruction` 较为简略。

**InkOS 优势**：InKOS 的审计维度注释非常详尽，特别是：
- 伏笔维度：带升级规则（promoted/core_hook/stale/blocked 分级处理）
- 节奏维度：带波形分析（蓄压→升级→爆发→后效周期检测）
- 角色弧线维度：带三连问检查（为什么这么做/符合人设吗/读者觉得突兀吗）

**增强建议**：对以下 5 个维度深化检查指令：
1. 伏笔检查 → 融入伏笔健康系统的诊断结果
2. 节奏检查 → 融入节奏分析器的确定性检测结果
3. 章节备忘偏离 → 细化 7 段 memo 的逐段对照
4. 配角降智 → 增加三连问检查指引
5. 爽点虚化 → 增加欲望驱动检查指引

**预估工作量**：1.5 人日

## 三、性能优化方向

### 3.1 当前性能表现

**积极面**：
- ✅ 代码分割做得好：ProjectEditor 的 10 个主要组件全部使用 `defineAsyncComponent` 懒加载
- ✅ Sandbox 组件（EntityTree、SandboxDocument、PlotLoomBoard 等）也已懒加载
- ✅ Chapters.vue 的子组件（ExportSettings、WriteNextDialog 等）懒加载
- ✅ pipelineWorker.ts 已就位，支持后台执行

**需改进**：

#### 性能 P1：大项目章节列表（100+ 章）无虚拟滚动

**现状**：Chapters.vue 渲染所有章节列表项，无虚拟滚动。当章节数量超过 100 时，DOM 节点过多导致滚动卡顿。

**建议**：使用 `el-table-v2`（Element Plus 虚拟表格）或 `@tanstack/vue-virtualizer` 对章节列表做虚拟化。

**预估工作量**：1 人日

#### 性能 P2：IndexedDB 全量加载

**现状**：`storage.ts` 使用 `index.getAll(IDBKeyRange.only(projectId))` 一次性加载项目的全部章节数据。对于 200+ 章的大型项目，首次加载可能超过 1 秒。

**建议**：
1. 首次加载仅加载章节元数据（id、number、title、wordCount、status），不加载 content
2. 正文内容按需加载（用户点击章节时再读取）
3. 使用 IndexedDB cursor 分页而非 getAll

**预估工作量**：1.5 人日

#### 性能 P3：Pipeline LLM 调用串行化

**现状**：PipelineRunner 的 Phase 1（Planner）→ Phase 2（Composer）→ Phase 3（Writer）→ Phase 5（Auditor）是完全串行的。每章需要 4-6 次 LLM 调用，单章耗时可能超过 60 秒。

**优化空间**：
- Phase 1（Planner）和 Phase 2（Composer）之间有依赖，必须串行
- Phase 5（Auditor）的确定性检查部分（AI标记词/敏感词/段落长度）可以在 Writer 输出的同时并行执行
- Phase 7-9（Settler/Analyzer/HookPromoter）中的 HookPromoter 是纯确定性逻辑，可以在 Settler 的 LLM 调用期间并行

**建议**：识别可并行的阶段，使用 `Promise.all` 优化。预期可减少 10-15% 的总耗时。

**预估工作量**：1 人日

#### 性能 P4：大章节编辑器性能

**现状**：ChapterEditorDialog（1,258 行）使用 tiptap 编辑器渲染整章正文。对于 5000+ 字的章节，编辑器初始化和 AI 重写面板的响应可能变慢。

**建议**：对超长章节（>8000 字）启用编辑器虚拟渲染或分段加载。

## 四、用户体验优化

### 4.1 Tour 引导重复问题

**现状分析**：

| 引导类型 | 触发条件 | 持久化 | 问题 |
|----------|----------|--------|------|
| OnboardingDialog | `useOnboarding().initialize()` → 检查 localStorage | `ai-novel-workshop:onboarding:c2:completed` | ✅ 完成后不重复，但 dismiss（"稍后继续"）后下次还会弹出 |
| SandboxLayout el-tour | `onMounted` 检查 localStorage | `ai-novel-workshop:sandbox-tour:completed` | ✅ 完成后不重复 |

**问题 1：OnboardingDialog "稍后继续"后反复出现**

`useOnboarding` 的 `dismiss()` 方法只设置 `isVisible = false`，但不写入 localStorage。因此每次刷新页面或重新进入项目编辑器时，`initialize()` 会再次弹出引导。

**修复建议**：`dismiss()` 应写入一个临时标记（如 `dismissed-at` 时间戳），24 小时内不再弹出。或者改为"下次进入时提醒"而非"每次都提醒"。

**预估工作量**：0.5 人日

**问题 2：缺少 Pipeline 首次使用的引导**

用户首次点击「一键续写」时，没有任何引导说明 Pipeline 是什么、将经历哪些阶段。WriteNextDialog 只有配置选项，没有功能说明。

**修复建议**：在 WriteNextDialog 中增加简要说明区域，或首次打开时显示 tooltip/mini-tour。

**预估工作量**：0.5 人日

### 4.2 错误反馈优化

**现状**：PipelineRunner 失败时返回的技术性错误信息直接展示给用户。

**建议**：
1. 按错误类型分类：API 限流、模型不可用、Token 超限、网络超时
2. 每种类型提供用户可操作的建议
3. 审计未通过时展示维度得分雷达图（而非原始 issue 列表）

### 4.3 Pipeline 进度面板 Agent 阶段可视化

**现状**：PipelineProgressPanel 展示章节级进度，但缺少 Agent 阶段时间线。

**建议**：在当前章节进行中时，显示 10 个 Agent 的执行状态条：
```
准备 ✅ → 规划 ✅ → 组装 ✅ → 写作 🔄 → 标准化 ⏳ → 审计 ⏳ → 修订 ⏳ → 沉淀 ⏳ → 分析 ⏳ → 伏笔 ⏳
```

**预估工作量**：1.5 人日

## 五、数据管理增强

### 5.1 Pipeline 运行状态持久化

**现状**：批量续写过程中刷新页面，进度全部丢失。

**建议**：
1. 将 Pipeline 运行状态（当前章节、已完成列表、配置参数）持久化到 IndexedDB
2. 页面加载时检测未完成任务，弹出"恢复续写"确认框
3. checkpointManager 已有 IndexedDB 基础设施，可复用

**预估工作量**：1.5 人日

### 5.2 Daemon 计数器持久化

**现状**：`DaemonService` 的 `chaptersCompletedToday` 和 `tokensUsedToday` 在刷新后重置为 0，每日限额保护形同虚设。

**建议**：将计数器按日期键存储到 IndexedDB（如 `daemon-counters:2026-05-29`），Daemon 初始化时读取。

**预估工作量**：0.5 人日

## 七、结论

第二轮迭代的 P0 功能（伏笔健康 333 行 + 写作方法论 162 行 + 大纲翻页）已全部落地，POV 过滤器和长跨度疲劳检测也已完成。

当前系统与 InkOS 的核心差距已从「架构缺失」缩小到「深度不足」：
- **上下文治理**：工坊用固定预算截断，InKOS 用意图感知排序 → 差距约 2 人日工作量
- **节奏分析**：工坊靠 LLM 判断，InKOS 有确定性模式检测 → 差距约 1.5 人日
- **性能**：大项目加载和列表渲染有优化空间 → 差距约 2.5 人日

建议本轮聚焦「质量深化 + 性能优化」，14 人日可覆盖全部 12 项优化任务。
